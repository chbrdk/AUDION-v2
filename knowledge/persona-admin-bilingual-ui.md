# Persona admin bilingual UI

- **Canonical English** lives in `personas` columns / `profile` JSON. **German mirror** is `profile_de` (same keys as `profile` where applicable) plus `headline_de`.
- **Admin translate API**: `POST /api/persona-admin/{persona_id}/translate-fields` with `{ "from_locale": "en"|"de", "strings": { "headline": "...", "bio": "..." } }`. Next.js must expose `app/api/persona-admin/[personaId]/translate-fields/route.ts` (proxy to persona-api). Web helper: `apps/web/lib/persona-translate-fields.ts` + path `API_ROUTES.personaAdminTranslateFields` in `apps/web/lib/api-routes.ts`.
- **UX**: One visible field per concept in the current UI language; on save, the other locale is filled via translate (fallback: `mirrorFillStringPair` in `apps/web/lib/bilingual-mirror.ts`).
- **PATCH `profile_de`**: The API requires `json_shape_compatible(profile, profile_de)` (same keys everywhere, matching list lengths and nested object keys). Use `alignProfileDeToEnProfile` in `apps/web/lib/persona-profile-de-shape.ts` after merging partial DE updates so the payload is never a sparse object.
- **Values / interests / social / communication / pain points / goals**: Same pipeline: flat keys (`value_0`, …) via `buildTranslateStringMap`, translate, apply to the other mirror. **English UI** en→de into `profile_de`; **German UI** de→en into `profile` (lists also overlaid from `profile_de` in `profileForChips`).
- **Traits** (`Record<string, number>`): API requires **identical trait keys** on `profile` and `profile_de` (`json_shape_compatible`). After every chip save, `profile_de.traits` is set from `profile.traits`. **German UI**: trait chip labels (underscore keys shown with spaces) are sent as `traitk_0`, … to translate-fields (**de→en**); both mirrors get the **English** slug keys and the same numeric values (`rebuildTraitsAfterDeKeyTranslation` in `persona-profile-bilingual-save.ts`). **English UI**: no trait-key translation (chips stay your English keys); mirrors stay in sync. Trait chips in DE admin still read from `profile` keys (English after save), unlike values which read from `profile_de` strings.
- **Saves**: `mergeEnProfileWithDeTranslation` → `buildTranslateStringMap` (+ `traitk_*` on DE trait saves) → **`POST …/translate-fields`** when needed → **`alignProfileDeToEnProfile`** → **`PATCH`**. **Bio + demographics**: `handleBioDemographicsBilingualSave` + `profileForBioEditor`.
- **Manual QA (DevTools Network)**: After editing e.g. **Interessen** chips and saving, expect **translate-fields** first with flat keys `interest_0`, `interest_1`, … then the persona **update** request carrying aligned `profile` and `profile_de` with mirrored list lengths.
- **Persona admin AI chips** (interests, values, goals, pain points, traits, vocabulary): Web passes `generated_text_locale_name` (`German` / `English`) from the active UI locale; `apps/api/app/prompts/templates.yaml` uses `${generated_text_locale_name}` so suggestions match the editor language. Merge lists use `profileForChips ?? profile` so DE UI extends German lists; saves still go through `mergeEnProfileWithDeTranslation`. `_enrich_persona_context` merges **caller context after** DB persona context so `generated_text_locale_name` is not overwritten; default remains German when omitted.
- **Chat system prompt** is not shown on the persona admin page; use **Ensure chat prompt** or server flows to update it.
