# Persona admin bilingual UI

- **Canonical English** lives in `personas` columns / `profile` JSON. **German mirror** is `profile_de` (same keys as `profile` where applicable) plus `headline_de`.
- **Admin translate API**: `POST /api/persona-admin/{persona_id}/translate-fields` with `{ "from_locale": "en"|"de", "strings": { "headline": "...", "bio": "..." } }`. Next.js must expose `app/api/persona-admin/[personaId]/translate-fields/route.ts` (proxy to persona-api). Web helper: `apps/web/lib/persona-translate-fields.ts` + path `API_ROUTES.personaAdminTranslateFields` in `apps/web/lib/api-routes.ts`.
- **UX**: One visible field per concept in the current UI language; on save, the other locale is filled via translate (fallback: `mirrorFillStringPair` in `apps/web/lib/bilingual-mirror.ts`).
- **PATCH `profile_de`**: The API requires `json_shape_compatible(profile, profile_de)` (same keys everywhere, matching list lengths and nested object keys). Use `alignProfileDeToEnProfile` in `apps/web/lib/persona-profile-de-shape.ts` after merging partial DE updates so the payload is never a sparse object.
- **Values / interests / social / communication / pain points / goals**: Same pipeline: flat keys (`value_0`, …) via `buildTranslateStringMap`, translate, apply to the other mirror. **English UI** en→de into `profile_de`; **German UI** de→en into `profile` (lists also overlaid from `profile_de` in `profileForChips`).
- **Traits** (`Record<string, number>`): API requires **identical trait keys** on `profile` and `profile_de` (`json_shape_compatible`). After every chip save, `profile_de.traits` is set from `profile.traits`. **German UI**: trait chip labels (underscore keys shown with spaces) are sent as `traitk_0`, … to translate-fields (**de→en**); both mirrors get the **English** slug keys and the same numeric values (`rebuildTraitsAfterDeKeyTranslation` in `persona-profile-bilingual-save.ts`). **English UI**: no trait-key translation (chips stay your English keys); mirrors stay in sync. Trait chips in DE admin still read from `profile` keys (English after save), unlike values which read from `profile_de` strings.
- **Saves**: `mergeEnProfileWithDeTranslation` → `buildTranslateStringMap` (+ `traitk_*` on DE trait saves) → **`POST …/translate-fields`** when needed → **`alignProfileDeToEnProfile`** → **`PATCH`**. **Bio + demographics**: `handleBioDemographicsBilingualSave` + `profileForBioEditor`.
- **Manual QA (DevTools Network)**: After editing e.g. **Interessen** chips and saving, expect **translate-fields** first with flat keys `interest_0`, `interest_1`, … then the persona **update** request carrying aligned `profile` and `profile_de` with mirrored list lengths.
- **Persona AI locale (single pipeline)**: Canonical **`output_locale`**: `"en"` \| `"de"` (aliases `locale`, `ui_locale`). Web admin passes `output_locale` from `useI18n().locale`. **`finalize_ai_locale_context`** (`apps/api/app/services/persona_ai_locale.py`) always derives **`generated_text_locale_name`** (`English` / `German`) for `templates.yaml`. **`persona_profile_for_ai`**: when `output_locale` is `de`, merge list + communication + bio-like fields from **`profile_de`** over `profile` (same idea as web `profileForChips`). Used by **`persona_ai_context.build_*`** (HTTP `/ai-assist` enrich + direct **`POST /personas/{id}/ai/*`** + **`POST …/enrich`** body `output_locale`). **`AiAssistService._build_context`** also runs `finalize_ai_locale_context` so any `generate()` path gets consistent template vars.
- **Locale guard footer**: After rendering, **`AiAssistService.generate`** / **`test_prompt`** append **`locale_output_guard_footer`** from `persona_ai_locale.py` (German vs English “KRITISCH” / “CRITICAL” block). For templates with **prefix/suffix cache split**, the footer is appended to **`prompt_suffix`** so OpenAI/Anthropic still receive it (the split path does not use the standalone `prompt` string). **`suggest_personas`** / **`suggest_target_groups`** append the same footer to the user message.
- **`POST /ai-assist` + `persona_id`**: After merging client context with `build_persona_*`, **`_enrich_persona_context`** re-applies server keys for **`persona_profile`**, **`persona_values`**, **`persona_interests`**, **`persona_goals`**, **`persona_pain_points`** (and traits/vocabulary/sentence_structure bio+profile fields) so a client-sent English **`persona_profile` JSON** cannot override **`persona_profile_for_ai`**. Admin chip AI calls should include **`persona_id`** and rely on the API for profile text (same pattern as pain points).
- **`POST /personas/{persona_id}/enrich`**: After merging AI chips, the API runs the same **translate + `align_profile_de_to_en_profile`** path as the admin (`merge_persona_profile_bilingual_enrich` in `apps/api/app/services/persona_profile_translate_merge.py`) and PATCHes **`profile_de`** when translation succeeds. If translate is unavailable (e.g. OpenAI not configured), enrich still saves **`profile`** only and logs `persona.enrich.bilingual_skipped`. The web client should send **`output_locale`** (`"en"` \| `"de"`) in the JSON body (persona admin, project “Create & enrich”, proxies) so enrich AI matches the UI language. **`enrich_profile_patch_json`** must use **snake_case keys only** (`pain_points`, `communication_style`) — camelCase aliases (`painPoints`, `communicationStyle`) break `json_shape_compatible` on save and caused HTTP 500 on enrich.
- **`POST /target-groups/{id}/personas/generate`**: `PersonaGenerationService.generate` always builds **`profile_de`** via **`_translate_profile_json_en_to_de`** assuming **`profile` strings are English**. Web **must not** send **`output_locale: "de"`** for default “create persona” flows if bilingual storage is desired (DE UI used to forward `locale` → German-only `profile` and a broken DE mirror). Persona overview “Generate with AI”, target-group admin persona form, and **`MsqdxGlassPersonaCreateDialog`** omit **`output_locale`** so **`profile`** stays English and **`profile_de`** is filled correctly.

## Journey & project AI locale

- **Journey phase AI** (`POST /journeys/{id}/ai/generate`): Request body may include **`output_locale`**; the router runs **`finalize_ai_locale_context`** so templates get **`${generated_text_locale_name}`**. Journey templates in `apps/api/app/prompts/templates.yaml` (`journey.moments`, `journey.description`, `journey.phase.create`, `journey.full_generation`, `journey.phase.name`) include an explicit **LANGUAGE** line tied to that variable. The web passes **`outputLocale`** from `useI18n().locale` via `use-ai-assist` (`output_locale` on the wire). `use-ai-assist` merges **`context` into `phase_context`** for journey calls so in-form fields reach the backend.
- **Suggest target groups / suggest personas**: Optional **`output_locale`** on the POST body; services `suggest_target_groups` / `suggest_personas` steer the OpenAI prompt (`German` vs `English`). Project admin sends **`output_locale: locale`** with suggest and enrich requests.
- **Full journey generation** (`journey.full_generation`): **`POST /projects/{project_id}/generate-journey`** and **`POST /journeys/generate`** accept optional **`output_locale`**. `JourneyGenerationService._generate_with_context` runs **`finalize_ai_locale_context`** before `AiAssistService.generate`, so the same template LANGUAGE rules apply. Web: project admin “Generate journey” and **admin/journeys/new** “Generate with AI” send **`output_locale`**. Async Celery **`generate_journey_task`** accepts **`output_locale`** (passed when starting the task from `use_async`).
- **Chat system prompt** is not shown on the persona admin page; use **Ensure chat prompt** or server flows to update it.
